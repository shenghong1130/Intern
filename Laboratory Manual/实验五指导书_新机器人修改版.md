# 实验五指导书——新机器人修改内容

本文档只列出原《实验五指导书》中需要替换或补充的内容；未列出的 CNN 训练、HLS 仿真与综合等内容继续沿用原指导书。本实验只讨论如何生成并提交 FPGA Artifact，以及如何取得分类结果。机器人开机、AprilTag、定位和路径规划分别见实验一至实验四。

当前实验平台为 TonyPi + Raspberry Pi + Kria KV260/PYNQ。本实验的 Artifact 上传和 FPGA 计算统一使用 HTTP。

---

## 一、实验目标

1. 理解 CNN 训练代码与 HLS C/C++ 前向计算之间的对应关系。
2. 使用 HLS 将 CNN 前向计算导出为硬件 IP，并在 Vivado 的 Kria KV260 工程中连接 Zynq UltraScale+ MPSoC、AXI DMA 和 CNN IP。
3. 生成 PYNQ Overlay 所需的 `<design>.bit` 和 `<design>.hwh`，组成可部署的 FPGA Artifact。
4. 通过 HTTP 将 Artifact 上传到 Central Server，提交 FPGA 计算并读取分类结果。
5. 理解 KV260 Worker 内部从 Overlay 加载、DMA 传输到 FPGA CNN 分类的执行过程。

本实验的主线为：

```text
CNN 训练 / HLS
    ↓
Vivado Block Design
    ↓
.bit + .hwh
    ↓ HTTP
Central Server
    ↓ 调度与部署
KV260 Worker
    ↓
PYNQ Overlay → AXI DMA → CNN IP → 分类结果
```

## 二、考核要求

- 【考核 1】HLS C Simulation 的输出与 Python/CNN 参考结果一致，并能完成 C Synthesis 和 Export RTL。
- 【考核 2】能够在 Kria KV260 工程中正确连接 PS、AXI DMA 与 CNN IP，完成 Validate Design、Generate Bitstream，并找到配套的 `.bit` 和 `.hwh`。
- 【考核 3】能够上传 FPGA Artifact，记录返回的 `artifact_id`，提交一次计算请求，并正确处理同步完成或排队两种响应。
- 【考核 4】能够解释 `.bit`、`.hwh`、Overlay、AXI DMA 和 CNN IP 在完整链路中的作用，并如实记录尚未接入真实 KV260 Worker 时的验证边界。

具体分值和现场验收数据集以课程最终通知为准。

## 3.2 CNN 与 HLS

原指导书以下内容仍然适用：

1. 使用训练数据运行 CNN 训练程序，得到网络参数。
2. 将网络参数和测试样例导出为 HLS 工程使用的头文件。
3. 保证 Python 网络结构、HLS C/C++ 前向计算和参数排列一致；修改网络结构时，必须同步修改 HLS 实现。
4. 在 HLS 工程中添加 CNN 源文件、参数文件、测试样例和 Testbench，设置正确的 Top Function。
5. 先运行 C Simulation，将中间层或最终输出与软件参考结果对照；通过后再运行 C Synthesis 和 Export RTL。

导出 IP 前至少检查：

- 输入尺寸、数据类型和通道顺序与运行端预处理一致；
- 输出数量与花卉类别数一致；
- CNN IP 的 AXI-Stream/控制接口与 Vivado Block Design 的连接方案一致；
- 综合报告中的时序与资源使用没有阻止后续实现的错误。

## 3.3 生成 FPGA 硬件

### 3.3.1 HLS 导出 CNN IP

沿用原指导书中的 C Simulation、C Synthesis 和 Export RTL 流程，但将旧平台 Part 替换为课程 KV260 工程使用的器件。不要仅凭旧截图选择器件。

### 3.3.2 Vivado Block Design

在 Vivado 中建立 Kria KV260 工程并加入：

- Zynq UltraScale+ MPSoC Processing System；
- AXI DMA；
- HLS 导出的 CNN IP；
- 自动连接所需的 AXI Interconnect/SmartConnect、时钟和复位模块。

当前参考 Overlay 中的主要实例名为：

```text
zynq_ultra_ps_e_0
axi_dma_0
test_0
```

名称可随工程改变，拓扑必须保持：

```text
PS DDR
  ↕ AXI Memory-Mapped
AXI DMA
  ↓ MM2S / AXI-Stream
CNN IP
  ↓ AXI-Stream / S2MM
AXI DMA
  ↕
PS DDR
```

当前参考 `.hwh` 中 AXI DMA 版本为 7.1，Scatter Gather 关闭，MM2S 与 S2MM 均启用。最终工程应使 PYNQ 能够取得发送和接收通道：

```python
overlay.axi_dma_0.sendchannel
overlay.axi_dma_0.recvchannel
```

完成 Block Automation 和 Connection Automation 后，逐项检查：

- AXI-Lite 控制通路；
- DMA 的 MM2S/S2MM 内存通路；
- DMA 与 CNN IP 的两条 AXI-Stream 通路；
- 时钟、复位和地址分配；
- Validate Design 的错误与 Critical Warning。

不要沿用原指导书中“统一忽略 OCM Critical Warning”的结论。只有课程基准工程明确允许忽略的警告才可保留。

### 3.3.3 生成 Bitstream

依次完成：

```text
Create HDL Wrapper
    ↓
Validate Design
    ↓
Run Synthesis
    ↓
Run Implementation
    ↓
Generate Bitstream
```

生成过程耗时与电脑配置、Vivado 版本和设计规模有关。不能仅以进度完成判断成功，还应确认实现过程没有失败，并检查生成文件。

## 3.4 FPGA Artifact

本实验最终必须得到相互匹配的两个文件，例如：

```text
design_1_wrapper.bit
design_1_wrapper.hwh
```

若工程名称不同，则记为：

```text
<design>.bit
<design>.hwh
```

- `.bit` 是 FPGA Configuration Bitstream，用于配置 KV260 的 PL。
- `.hwh` 是硬件描述元数据。PYNQ 使用它识别硬件 IP、AXI 地址、DMA 和接口信息。

二者必须来自同一次 Vivado 设计生成，并作为一个整体上传。只上传 `.bit`，或混用不同工程/不同版本的 `.bit` 与 `.hwh`，都不是有效 Artifact。

常见输出位置为：

```text
<project>.runs/impl_1/<design>.bit
<project>.gen/sources_1/bd/<design>/hw_handoff/<design>.hwh
```

Vivado 版本的目录结构可能不同，应以当前工程实际输出为准。

## 3.5 通过 HTTP 上传 FPGA Artifact

目标教学架构为：

```text
Student / Client
        │
        │ HTTP
        ▼
Central Server :8000
        │
        │ 保存、版本管理、调度和部署
        ▼
KV260 Worker :8080
        │
        ▼
PYNQ / Overlay / AXI DMA / FPGA
```

学生原则上只访问 Central Server，不直接选择或硬编码某一台 KV260 Worker。Central Server 负责保存 Artifact、选择可用 Worker、部署硬件文件和转发计算。

课程对外 Artifact 接口为：

```text
POST /fpga/artifacts
Content-Type: multipart/form-data
```

表单字段为 `student_id`、`bit` 和 `hwh`。上传示例：

```bash
CENTRAL=http://<CENTRAL_SERVER_IP>:8000

curl -X POST "$CENTRAL/fpga/artifacts" \
  -F student_id=student01 \
  -F bit=@design_1_wrapper.bit \
  -F hwh=@design_1_wrapper.hwh
```

成功响应中的 `artifact_id` 是后续计算所用的 Artifact 标识。课程部署版应为同一学生的连续上传维护 `v1`、`v2`、`v3` 等版本；具体版本字段以现场 API 响应为准。

> 实现边界：当前仓库固定的 `FPGA_code` 子模块快照中，Central Server V1 的上传端点还要求 `project_name` 和 `version`，并采用 Session/Lease API；该快照没有顶层 `/predict` 和 `/requests/{request_id}`。本节的简化公共接口必须以课程最终部署版本或其 OpenAPI 文档为准，不能把下文命令直接视为已在该本地快照验证通过。

不要将 `127.0.0.1` 写成学生远程访问地址。若课程尚未公布 Central Server IP，保留 `<CENTRAL_SERVER_IP>`。

## 3.6 提交 FPGA 计算

课程统一公共接口约定为：

```text
POST /predict
Content-Type: application/json
```

基本请求结构：

```json
{
  "student_id": "student01",
  "payload": {
    "课程定义的 CNN 输入": "..."
  }
}
```

真实 CNN 图片的编码、尺寸、通道顺序和字段名必须以课程提供的 KV260 PYNQ Worker 为准。当前 Central Server 已有 Artifact、调度与转发框架；本地仓库中的真实 PYNQ CNN Worker 尚未接入该 Central Server。不要把 Mock Worker 测试使用的 `{"value": 123}` 写成正式 CNN payload。

请求处理流程为：

```text
POST /fpga/artifacts
        ↓
获得 artifact_id
        ↓
POST /predict
        ↓
   ┌────┴────┐
   │         │
200         202
completed   queued
   │         │
   │         ▼
   │   GET /requests/{request_id}
   │         │
   └────┬────┘
        ▼
读取 completed 结果
```

- HTTP `200` 且状态为 `completed`：直接读取分类结果。
- HTTP `202` 且状态为 `queued`：保存 `request_id`，使用 `GET /requests/{request_id}` 查询，直到 `completed` 或课程规定的超时时间。
- 其他状态：记录 HTTP 状态码、响应正文和 `request_id`，按课程部署版错误说明处理，不要无限重试。

## 3.7 KV260 内部执行原理

仓库中的 `robot_code/robot_tonypi/fpga_flower_server/fpga_server_api_ready.py` 可用于理解单板 FPGA 分类过程：

```text
.bit + .hwh
    ↓
PYNQ Overlay
    ↓
allocate 输入/输出缓冲区
    ↓
AXI DMA sendchannel
    ↓
CNN FPGA IP
    ↓
AXI DMA recvchannel
    ↓
12 类输出
    ↓
argmax
    ↓
flower class
```

参考服务使用 `3 × 28 × 28` 的 `float32` 输入缓冲区和 12 个 `float32` 输出。它是理解 Overlay、DMA 和 CNN IP 的参考实现，不是完整 Central Server 架构的对外接口依据。

完整目标链路为：

```text
HTTP 请求
    ↓
Central Server 调度
    ↓
KV260 Worker 加载对应 Artifact
    ↓
PYNQ Overlay
    ↓
AXI DMA → CNN IP → AXI DMA
    ↓
分类结果
    ↓
HTTP 返回
```

当前仓库已实现 Central Server V1 和 Mock Worker；真实 KV260 PYNQ Worker、正式 CNN payload、部署启动方式和端到端硬件验证仍以课程最终部署版本为准。不得据此宣称多台真实 KV260 已完成 CNN 集群部署。

## 3.8 实验验证与提交记录

按以下顺序验收：

1. HLS C Simulation 与软件参考结果一致。
2. Vivado 成功生成相互匹配的 `.bit` 和 `.hwh`。
3. 记录两个文件的名称、大小和生成时间。
4. 上传 Artifact，保存 `artifact_id` 和版本信息。
5. 提交 Predict 请求；若返回 `202`，保存 `request_id` 并查询到终态。
6. 记录分类输入、预期类别、返回类别、置信度（若接口提供）、HTTP 状态码和总耗时。
7. 若使用 Mock Worker，只能记录为 Central Server 调度验证；接入真实 PYNQ Worker 后才能记录 FPGA CNN 硬件结果。

建议提交以下实验记录：

```text
student_id：
bit 文件：
hwh 文件：
artifact_id：
artifact 版本：
predict HTTP 状态：
request_id（如有）：
最终状态：
分类结果：
是否为真实 KV260 PYNQ Worker：是 / 否
```

FPGA 分类只负责得到当前屏幕花卉类别；比赛中的机器人身份注册和换花请求属于上层比赛交互流程，当前通过 NFC 完成，具体见《机器人比赛说明_新机器人修改版.md》。
